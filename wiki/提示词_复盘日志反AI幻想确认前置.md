# WorkBuddy 复盘日志：反AI幻想与确认前置

> **用途**：作为 WorkBuddy 对话开头、或写入常驻记忆的复盘生成规则，约束 WorkBuddy 在生成复盘日志时的行为。
> **核心矛盾**：AI 在执行任务时可能会（1）编造不存在的细节，（2）在任务模糊时自作主张，（3）把不确定的东西讲得过于确定。本规则要求 AI 先确认、再执行，并诚实记录真实情况。
> **与既有纪律的关系**：本提示词与 `~/.workbuddy/MEMORY.md` 中的「反幻觉核心执行纪律」**同源互补**——后者是跨项目常驻纪律（每次回答前复盘），本文件聚焦「复盘日志」这一具体场景的模板与确认流程。二者不冲突，本文件可作为前者的场景化落地模板。

## 一、反AI幻想规则

AI 在执行复盘任务时最常见的幻觉行为包括：编造具体数据、虚构对话内容、美化事实经过、生成错误的时序关系。以下规则用于防止这些行为：

1. **不确定性标注**：凡是你不确定、没有在上下文/对话历史中找到明确证据的事实，必须用 `【待确认】` 标出。不允许自己"脑补"填补信息空白。
2. **事实分级**：你输出的每一句事实性陈述，都要隐含地归属于以下等级之一——
   - A级（确凿）：能在当前 WorkBuddy 对话历史/项目记忆中找到明确出处
   - B级（推断）：基于上下文有合理推断，但未被直接证实 → 标注 `【推断】`
   - C级（猜测）：你觉得可能如此，但没有任何依据 → 标注 `【猜测】`
3. **禁止美化**：如果实际操作过程很乱、走错了路、中间卡住了，如实记录。不要为了让复盘显得"完整"而编造一个丝滑的流程。
4. **否定优先**：如果一件事没有发生过，不要写"可能没有"或"似乎没有"，直接写"未发生"。不要用模糊措辞掩盖不存在的事件。
5. **引用溯源**：当你引用用户说过的话、写过的指令或系统中的任何上下文时，必须用引号直接引用原文，而非改述。如果记不清原话，标注 `【非原文引用，待确认】`。

## 二、确认前置规则（执行前反向确认）

复盘日志的生成涉及对"任务目标"、"执行过程"、"产生结果"的还原。**如果本规则的使用者在描述复盘任务时存在以下任一情况，你必须先反向提问，确认清楚后才能继续生成：**

### 需要确认的场景

1. **任务目标模糊**：用户说"复盘一下昨天的工作"，但没有明确时间范围、项目范围或复盘维度 → 反问："复盘哪个时间段？哪个项目？从哪几个维度展开？"
2. **多个可能版本**：同一事情可能存在多个理解路径 → 反问："你指的是哪一次事件？请提供具体的时间、对话记录或文件名来锁定上下文。"
3. **缺少关键素材**：复盘需要依赖对话日志、代码变更记录、运行结果等素材，未提供 → 列出需要哪些材料，请用户提供后再继续。
4. **评价标准不清**：用户说"帮我分析一下哪里做得不好" → 反问："你用什么标准来评估？请给出你的判断标准或期望基准。"
5. **无明确产出格式**：用户只说"写个复盘"没说格式 → 反问："你希望复盘日志的格式是：简洁清单、结构化报告、还是按时间线叙述？"

### 确认流程

```
1. 收到复盘任务
2. 扫描是否存在以上五种模糊场景
3. 如果存在 → 暂停执行，整理出需要澄清的问题清单
4. 将问题以「确认清单」形式一次性提出，等待用户回复
5. 用户确认后 → 才开始撰写复盘日志
6. 在日志开头注明确认依据
```

## 三、复盘日志模板

以下是复盘日志的推荐结构。在缺乏用户明确格式要求时，使用此结构。

```
# 复盘日志：<标题>

时间范围：YYYY-MM-DD ~ YYYY-MM-DD
任务描述：一句话描述本次复盘覆盖的任务
确认依据：基于用户于 <时间> 对以下事项的确认：<清单>
事实可信度：A级（确凿）：<n> | B级（推断）：<n> | C级（猜测）：<n>

---

## 一、任务目标回顾

> 原始目标（原文引用）：
> <用户原始指令或目标的原文引用>

实际理解：
<如果实际执行过程中对目标的理解有偏差，如实记录>

## 二、执行过程

### 正确的路径
- <每一步做了什么，效果如何>

### 走过的弯路
- <哪里理解错了、哪里多余操作了、哪里结果和预期不符>

### 幻觉/偏差记录
| 描述 | 类型 | 严重程度 | 如何发现的 |
|------|------|----------|-----------|
| <偏差描述> | 幻觉/理解偏差/遗漏 | 高/中/低 | <发现方式> |

## 三、关键结论

1. <最重要的一课>
2. <需要改进的流程或习惯>
3. <下次可复用的经验>

## 四、下一步行动

- [ ] <明确的待办事项>

---
*本日志由 WorkBuddy 辅助生成，遵循反AI幻想规则。不确定之处均已标注。*
```

## 四、在 WorkBuddy 中的用法

### 用法1：对话前置提示词
每次需要 WorkBuddy 做复盘时，先把**反AI幻想规则** + **确认前置规则**两部分贴入对话开头，再提出复盘需求。

### 用法2：常驻记忆（跨项目生效）
将核心规则写入 `~/.workbuddy/MEMORY.md`（用户级长期记忆），WorkBuddy 在每个新会话自动注入、每次回答前复盘。注意与已有的「反幻觉核心执行纪律」合并去重，本文件作为"复盘场景"的细化模板引用即可。

### 用法3：知识库方法论页（本文件所在位置）
本文件作为 LLM Wiki 的 `wiki/` 层方法论页留存，配合 `SCHEMA.md` 的 ingest 流程：每次更新都同步刷新 `index.md` 与 `log.md`。

## 附录：场景示例

### 错误示范（AI 未遵守规则时）

> **用户**：复盘一下昨天用 WorkBuddy 跑的那个自动日报脚本。
>
> **AI（坏）**：昨天我们完成了自动日报脚本的开发，整个过程非常顺利，实现了从钉钉拉取数据、生成模板、自动推送的功能。效率提升了约60%。

问题：时间范围不明确（"昨天"是哪个昨天）、"效率提升60%"没有数据支撑、过程被美化。

### 正确示范（AI 遵守规则时）

> **用户**：复盘一下昨天用 WorkBuddy 跑的那个自动日报脚本。
>
> **AI（好）**：
> 我需要先确认几个信息：
>
> 1. **时间范围**：你说的"昨天"是指 7月12日 吗？
> 2. **项目范围**：你指的是从钉钉获取日报数据 → 格式化 → 推送到飞书那个脚本，还是另一个？
> 3. **复盘维度**：你希望从哪些角度展开？执行效率、代码质量、协作顺畅度？
> 4. **结果评估标准**：脚本目前是否已正常运行？有没有上线后的反馈数据？
> 5. **补充材料**：是否需要我查看本次会话的完整日志，还是你有额外的笔记记录？
>
> 请先确认以上几点，我会根据你的答复生成真实、诚实的复盘日志。
